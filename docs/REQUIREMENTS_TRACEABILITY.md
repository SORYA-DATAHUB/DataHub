## Header block

**Purpose.** Prove that every SRS requirement traces backwards to a business requirement and forwards to design, user stories, planned tests and a planned implementation location, and expose any gap before implementation starts.

**Scope.** All requirement IDs present in SRS.md at generation time: 179 functional, 38 non-functional and 22 security requirements (239 total).

**Assumptions.** Implementation has not started; every status is `Planned`. Section references point at the v1.0 design documents and are re-checked when those documents change.

**Decisions.**
- The requirement list is generated by parsing every `| FR-… | NFR-… | SEC-… |` row of SRS.md, so no requirement can be missed; counts are cross-checked against SRS §2.
- BR source = BR IDs in the SRS *Source* column ∪ the SRS §13 BR → requirement table.
- **Planned test ID rule** (shared with TEST_CASES.md): `FR-<MOD>-nn` → `TC-<MOD>-0nn` (e.g. FR-PAY-07 → TC-PAY-007); `NFR-<CAT>-nn` → `TC-<CAT>-0nn`; `SEC-nn` → `TC-SEC-0nn`; collision exception `NFR-UPL-nn` → `TC-UPLR-0nn`.
- Implementation location: backend module path under `apps/api/src/datahub/` per LLD §1 / §1.2, plus the web routes (UI_UX_DESIGN.md §3) of the linked stories.
- Design reference abbreviations: LLD, SDD, HLD, SAD (`02-system-architecture/`), DB = DATABASE_SCHEMA.md, API = API_DOCUMENTATION.md, AUTH_AUTHORIZATION / FILE_UPLOAD_STORAGE (`04-backend-api/`), UI_UX_DESIGN / DESIGN_SYSTEM (`03-ui-ux-design/`), ADR-nnnn (`02-system-architecture/ADR/`).

**Dependencies.** SRS.md, BRD.md, USER_STORIES.md, LLD.md, SDD.md, DATABASE_SCHEMA.md, API_DOCUMENTATION.md, AUTH_AUTHORIZATION.md, FILE_UPLOAD_STORAGE.md, UI_UX_DESIGN.md; TEST_CASES.md (planned IDs).

**Acceptance criteria for this document.**
1. Every SRS requirement appears exactly once in §3 (239 rows; SRS §2 declares 227 for the original catalogue).
2. Every row has a BR source or an explicit baseline source, a design reference, a planned test ID, an implementation location and a status.
3. Every BR-01 … BR-34 maps to ≥ 1 requirement (§4).
4. Requirements without a user story are listed with a reason (§5).
