## Status

## Context

Reviewers and annotators must view PDFs, TIFFs and images inside the app. MASTER Part 6 lists PDF.js. Rendering untrusted PDFs in the browser exposes every viewer to parser exploits and font/JS features, requires downloading entire originals (up to 4,000,000,000 bytes under AM-01) to the client, and behaves differently across browsers. Annotation tasks are page-based, so stable per-page images are useful anyway.

## Decision

Render pages server-side in the processing worker: PDFs with pypdfium2 (≤ 500 pages rendered), TIFF/images with Pillow (WebP derivative ≤ 4096 px, multi-page TIFF as pages). Text formats get extracted text previews (python-docx, striprtf, ODT XML via defusedxml); DOC has no preview (A-11). The browser displays images fetched through authorised presigned URLs and implements zoom, pan and rotation client-side. PDF.js is not used in v1.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| PDF.js in the browser | Native text layer and selection, but ships untrusted originals to every reviewer, large downloads, inconsistent rendering, larger attack surface. |
| LibreOffice-based conversion for Office documents | Broader preview coverage, but large image, slow, history of CVEs; excluded in v1 (A-11). |
| Third-party document viewer service | Sends confidential documents to a third party; cost. |

## Tradeoffs

+ Viewers only receive inert raster images and plain text; consistent rendering.
+ Page images double as annotation task units.
− No native text selection on PDF pages; text-region selection uses image coordinates.
− Rendering costs worker CPU and storage for derivatives (bounded by page and pixel limits).

## Consequences

- `file_previews` stores per-page keys; previews are regenerated by `POST /admin/files/{id}/rescan`.
- Revisit PDF.js or a sandboxed viewer in v2 if text-layer selection becomes a requirement.
